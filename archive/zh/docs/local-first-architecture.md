# Local first architecture

BeefTV's desktop is built as a single-user, local-first workspace. The desktop only starts one Wails process: Wails hosts the front end, and the Go runtime provides the loopback API and SQLite/local resource directory.

## Running boundaries

```text
Wails
  ├─ React/Vite 前端
  └─ Go loopback API
       ├─ workspace / projects / canvas / tasks
       ├─ local resources（SQLite 元数据 + dataDir/resources 文件）
       ├─ local task worker
       └─ configured model providers（仅在用户主动生成时访问）
```

The local mode is determined by `Service.NewLocal` and `isLocalWorkspaceMode()`. It must satisfy:

- No registration login, payments, finance, object storage, SaaS model catalog and cloud sharing routing.
- No remote user data synchronization session is established; `saveRemoteUserDataNow` returns directly in local mode.
- Billing adopts no-op lifecycle; task success, failure, cancellation and retry do not read or modify the billing order.
- Materials are written to the Go local resource directory first; the browser IndexedDB is only used as a downgrade cache when the service is unavailable.
- Local asset selectors do not enumerate or write external plug-in asset sources; external model calls still only occur when actively generated by the user.
- Canvas, projects, materials, tasks and model configurations all use the local workspace as the only data source.

## Data flow

1. The user imports materials: the file is written to the local resource service, and SQLite saves the resource metadata.
2. User edit canvas: Zustand state is persisted to SQLite/local workspace file through local repository.
3. User submits and generates: the task enters the local queue; the reference media is first converted to local `resource:<id>` reference.
4. The model returns the result: the result is written to the local resource, and then the task materializer registers the material idempotently and binds the canvas/project.
5. Refresh or restart: Restore from the local workspace and resource directory, without relying on accounts or cloud baselines.

The model provider may still be an external API, which is a "generate call exit", not application data synchronization. The app does not upload canvas, library, or task records to SaaS storage.

## Module responsibilities

- `backend/internal/handler`: Native HTTP contracts and route-level dependency injection.
- `backend/internal/localapp`: Local composition root; assembled by workspace, project, asset, task, build, provider and agent port.
- `backend/internal/app`: Compatible adapter during migration period; new local functions must not continue to expand this single entry.
- `backend/internal/repository`: SQLite data access, does not carry cloud synchronization semantics.
- `web/src/services/*-repository`: Front-end local persistence entry.
- `web/src/services/user-data-sync.ts`: For hosted profile use only; any caller must go through the `isLocalWorkspaceMode()`/`hasRemoteUserDataSyncSession()` guard.
- `web/src/hooks/use-external-asset-sources.ts`: The local profile directly returns an empty external source to prevent plug-ins such as Eagle from initiating remote reading when the material selector is opened.

## Modify the rules

When adding a new feature, first decide whether it belongs to the "local workspace" or the "hosted compatibility layer." Local functions must not directly call `user-data`, `wallet`, `payments`, `/admin` or the remote resource import interface; when external models are required, only provider transport is used, and cloud persistence is not added.

```bash
BEEFTV_GO_DIR=/path/to/go ./scripts/verify-beeftv-local-release.sh
BEEFTV_GO_DIR=/path/to/go ./scripts/build-beeftv-release.sh
```

The browser acceptance script is located at `web/scripts/beeftv-local-*-audit.mjs` and covers routing network boundaries, material upload, refresh/restart recovery, Agent startup and model configuration.
