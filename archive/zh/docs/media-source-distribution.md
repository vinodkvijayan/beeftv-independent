# Licensing and source code delivery of media components

BeefTV retains existing FFmpeg media capabilities. The new source code availability terms in the root directory `LICENSE` only apply to the new original content agreed upon; historical MIT content and third-party components continue to apply to the original license. Third-party licenses cannot be overridden with an additional statement.

## Components and calling methods

| Components | Versions and Licenses | Usage |
| --- | --- | --- |
| Browser `@ffmpeg/core` | 0.12.10, GPL-2.0-or-later | Running in Worker, providing editing, cropping, merging, audio processing and exporting |
| Windows FFmpeg/ffprobe | BtbN n8.1.3-18-g46d899d7a0-20261019, GPL-3.0-or-later | Standalone command line process, exchange data through parameters and files |
| macOS ffprobe | FFmpeg 8.0.1, LGPL-2.1-or-later | Compile from fixed source, turn off GPL features and external libraries, independent process detection of media |
| Optional deep run package for Windows | Fixed BtbN build same as desktop; historical package also contains FFmpeg that comes with imageio-ffmpeg wheel | Python starts independent process; subsequent builds remove unused imageio-ffmpeg and keep imageio |

The native command line tool and browser WASM are used in different ways, and the licensing requirements for combined distribution need to be determined separately. Neither a stand-alone process, a Worker, nor a separate download automatically proves compatibility; nor does a third-party manifest replace corresponding source code delivery.

## Implemented Delivery

- Application version number → Update log → **Third-party license and source code**, you can view the project license, third-party list and the full text of GPL/LGPL.
- Web builds write these files to `/licenses/`; desktop packages are also placed in `agent-host/licenses/`, and macOS is under `Contents/Resources/` in the app and can be read offline.
- `sources.json` records the platform, component version, license and WASM file hash of this build. `upstream` is the entrance to the upstream project; `source` only records the source code package actually generated by this pipeline. If it is missing, it is `null`, and the page does not generate non-existent download links.
- macOS build of ffprobe also generates `BeefTV-vX.Y.Z-ffprobe-darwin-{arm64,amd64}-sources.tar.gz`, containing unmodified source code, license, actual build script, parameters and binary hash. The official desktop pipeline will upload it together with the installation package to the same version of GitHub Release.
- The browser core source code package `BeefTV-vX.Y.Z-ffmpeg-wasm-sources.tar.gz` contains 21 fixed-commit source code archives, licenses, upstream compilation scripts and offline build instructions. The formal desktop pipeline first generates the source code package, then writes its download information to the license page of each platform, and uploads it together with the installation package. Normal local/web builds only write download information when the source package is actually available.
- The Windows version, upstream ZIP, two executables, license and source code archive hash are all fixed at `licenses/ffmpeg-windows.json`. Both desktop and deepin builds call the same media packager, rejecting any system-installed FFmpeg. Both remain with the package `LICENSE.txt`, full `manifest.json`, and the same license copies required by the old updater `LICENSE` and `README.txt` provided by BeefTV; the deep run package rechecks the six files within the ZIP after compression and writes the corresponding information to the build metadata.

macOS source code package can be generated separately:

```sh
bash scripts/package-media-runtime-macos.sh darwin/arm64 ./media-runtime \
  ./ffmpeg-source.tar.gz ./BeefTV-vX.Y.Z-ffprobe-darwin-arm64-sources.tar.gz
```

The hashes recorded here are used to check the material, and engineering verification is not equated with a conclusion of legal compatibility.

Generate or check the WASM source package:

```sh
python3 scripts/package-wasm-sources.py --version vX.Y.Z \
  --binary-dir web/node_modules/@ffmpeg/core/dist/esm
python3 scripts/package-wasm-sources.py \
  --verify dist/BeefTV-vX.Y.Z-ffmpeg-wasm-sources.tar.gz
```

Fixed version list at `licenses/ffmpeg-wasm-sources.json`. Source code selection was based on upstream 0.12.10 release commits, dependency history, and existing core reported versions: FFmpeg 5.1.4, the exact commit of Emscripten 3.1.40, x264 core 164, and LAME 3.100 all matched. The source package retains `build/*.sh`, modified `src/fftools`, and binding code; the offline build recipe only changes the upstream download step to use archived files. No proof of signed build is provided upstream, and the source code package does not claim to be able to reproduce the npm product byte-for-byte. Recompiling and replacing the core yourself is another operation that requires functional verification.

Windows desktop and Deepin run packages use the same entry:

```powershell
./scripts/package-media-runtime-windows.ps1 -Destination ./build/media-runtime
./scripts/build-depth-runtime-windows.ps1 -Variant cpu -FFmpegDir ./build/media-runtime
```

The Windows source manifest bundles BtbN fixed build recipes, dependency images, FFmpeg commits, as well as three dependency cache shards and a supplemental source archive. The above components archive provides both these materials and build instructions with `SHA256SUMS`, and the license page links to the same archive. When replacing a build, the corresponding materials must be updated together; this archive does not claim that the complete toolchain can be rebuilt offline or byte by byte.

## Release Responsibility

Distributors should retain the attribution, license and applicable source code materials of each component, and provide the source code, modifications and necessary build scripts corresponding to the distributed binaries. The upstream homepage or version number itself does not constitute the delivery of complete corresponding source code.

History The dependent source code, patches and build materials of Gyan pre-built tools and imageio wheel embedded FFmpeg must be checked separately against the original binary; they cannot be replaced by the BSD license of the new BtbN source code, FFmpeg main source code or imageio Python package. Source package archives also do not automatically prove license compatibility of combined distributions.

The depth component reads the video through OpenCV and calls FFmpeg under the running package `bin/` to write the preview without using `imageio-ffmpeg`. Subsequent builds therefore remove this duplicate executable and actually read the video in the move self-test to confirm that the wheel is not needed. Old running packages that have been released must still be checked according to their actual contents. Removing dependencies for subsequent builds does not mean completing the source code of the old binary.
